# StockPilot --- AI Architecture: Fast Offline Response Implementation

**Status:** Implementation plan\
**Target:** StockPilot Mobile v1.x\
**Core:** Expo Router + Expo SQLite\
**Rule:** Generative AI is never on the critical path for showing
inventory intelligence.

## 1. Architecture decision

StockPilot should use two intelligence layers.

**Layer A --- Local Intelligence Engine** is always available offline.
It uses Expo SQLite, TypeScript rules, stock-movement history,
calculations, cached insight snapshots, and local response templates.

**Layer B --- Optional Generative AI** only explains or summarizes facts
already calculated by StockPilot. It must not own stock quantities,
modify inventory, invent missing records, bypass validation, or block
the initial UI.

``` text
SQLite owns facts
      ↓
Domain services own rules
      ↓
Local Intelligence Engine owns calculations
      ↓
Insight snapshots cache derived results
      ↓
UI renders immediately
      ↓
Optional generative AI enhances explanation
```

## 2. Fast-response plan

The app should return useful intelligence before doing optional
expensive work.

``` text
Open Insights
    ↓
Read cached snapshot
    ↓
Render immediately
    ↓
Check fingerprint/expiry
    ↓
Recalculate stale local insight in background
    ↓
Update snapshot
    ↓
Optionally request an AI explanation when online
```

Engineering targets, to be verified on real devices:

-   cached insight read: target under 50 ms where practical;
-   small local calculation: target under 100 ms where practical;
-   useful Insights content visible: target under 300 ms on supported
    devices;
-   generative AI: excluded from initial-render performance
    requirements.

These are StockPilot performance budgets, not guarantees from Expo.

## 3. Step 1 --- Optimize the SQLite foundation

At database initialization:

``` ts
await db.execAsync(`
  PRAGMA journal_mode = WAL;
  PRAGMA foreign_keys = ON;
`);
```

Expo recommends WAL for general SQLite performance. Keep inventory,
products, movements, settings, and insight snapshots in SQLite.

Use async SQLite APIs for non-trivial work. Expo warns that heavy
synchronous database operations can block the JavaScript thread.

Use bound parameters or prepared statements for input-derived queries.

## 4. Step 2 --- Build stock-health calculations

Create:

``` text
src/services/insights/
├── stock-health.service.ts
├── movement-analysis.service.ts
├── reorder.service.ts
├── insight-engine.service.ts
└── insight.types.ts
```

Example:

``` ts
export type StockHealth = "healthy" | "warning" | "critical";

export function calculateStockHealth(
  currentStock: number,
  reorderLevel: number
): StockHealth {
  if (currentStock <= 0) return "critical";
  if (currentStock <= reorderLevel) return "warning";
  return "healthy";
}
```

No network or LLM is involved.

## 5. Step 3 --- Calculate movement intelligence locally

Do arithmetic in deterministic code, not in an LLM.

``` ts
export function averageDailyOutflow(
  totalOutflow: number,
  days: number
): number {
  return days > 0 ? totalOutflow / days : 0;
}

export function estimatedDaysRemaining(
  currentStock: number,
  dailyOutflow: number
): number | null {
  return dailyOutflow > 0 ? currentStock / dailyOutflow : null;
}
```

Useful evidence includes current stock, reorder level, 7/30-day outflow,
average daily outflow, estimated days remaining, last movement, and
movement count.

## 6. Step 4 --- Query only required data

Never load all movement history for every render.

``` sql
SELECT product_id, SUM(quantity) AS total_out
FROM stock_movements
WHERE business_id = ?
  AND store_id = ?
  AND type = 'OUT'
  AND occurred_at >= ?
GROUP BY product_id;
```

Index fields frequently used for filtering:

``` text
business_id
store_id
product_id
occurred_at
type
```

Keep strict business/store isolation in every repository query.

## 7. Step 5 --- Add insight snapshots

Snapshots contain derived results, never authoritative inventory.

Suggested migration:

``` sql
CREATE TABLE insight_snapshots (
  id TEXT PRIMARY KEY NOT NULL,
  business_id TEXT NOT NULL,
  store_id TEXT NOT NULL,
  product_id TEXT,
  insight_type TEXT NOT NULL,
  severity TEXT NOT NULL,
  source TEXT NOT NULL,
  fingerprint TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  generated_at TEXT NOT NULL,
  expires_at TEXT,
  created_at TEXT NOT NULL
);

CREATE INDEX insight_snapshots_store_idx
ON insight_snapshots (business_id, store_id);

CREATE INDEX insight_snapshots_fingerprint_idx
ON insight_snapshots (fingerprint);
```

Preserve the composite foreign-key rules from the main StockPilot schema
when turning this sketch into the real migration.

Recommended sources:

``` text
LOCAL_RULE
GENERATIVE_AI
```

## 8. Step 6 --- Fingerprint the evidence

Create a fingerprint from only the facts that affect an insight.

``` ts
type InsightFingerprintInput = {
  productId: string;
  currentStock: number;
  reorderLevel: number;
  totalOutflow7d: number;
  totalOutflow30d: number;
  lastMovementAt: string | null;
};
```

Concept:

``` text
stock + reorder level + movement summary
                  ↓
              fingerprint
```

Same fingerprint plus a valid snapshot means return the cache. Do not
recalculate or call AI.

## 9. Step 7 --- Use stale-while-revalidate

``` ts
async function getFastInsight(request: InsightRequest) {
  const cached = await snapshotService.findLatest(request);

  if (cached) {
    void refreshIfNeeded(request, cached);
    return cached;
  }

  return generateLocalInsight(request);
}
```

Behavior:

1.  Read existing snapshot.
2.  Render it immediately.
3.  Determine whether its fingerprint or expiry is stale.
4.  If valid, stop.
5.  If stale, recalculate locally in the background.
6.  Store the new snapshot.
7.  Update UI only when the result changed.

## 10. Step 8 --- Precompute after inventory changes

After a stock transaction commits:

``` text
Inventory Service
      ↓
exclusive SQLite transaction
      ↓
commit stock movement + quantity
      ↓
invalidate affected insight
      ↓
recalculate only affected product
      ↓
save new snapshot
```

Do not regenerate every product because one product changed.

Keep inventory mutation and insight generation separate. An insight
failure must never roll back a valid stock transaction.

## 11. Step 9 --- Keep authoritative mutations exclusive

Stock changes continue through the inventory service.

``` ts
await db.withExclusiveTransactionAsync(async (txn) => {
  // verify business/store/product
  // read current stock
  // reject resulting quantity < 0
  // insert movement
  // update inventory
});
```

Expo documents `withExclusiveTransactionAsync()` for isolating queries
inside the transaction scope. This fits StockPilot's strict stock-update
boundary.

## 12. Step 10 --- Generate readable text locally

You do not need an LLM to explain basic inventory facts.

``` ts
type LocalInsight = {
  title: string;
  summary: string;
  severity: "info" | "warning" | "critical";
  evidence: {
    currentStock: number;
    reorderLevel: number;
    averageDailyOutflow?: number;
    estimatedDaysRemaining?: number;
  };
  recommendedAction?: string;
  generatedAt: string;
};
```

Example local output:

``` text
Rice 25kg is running low.

8 units remain.
Reorder level: 10.
Estimated remaining stock: about 3 days.

Recommended action:
Review restocking.
```

This is instant, predictable, testable, and offline.

## 13. Runtime flow

### App startup

``` text
Open SQLite
→ run migrations
→ enable foreign keys/WAL
→ load active store
→ read cached dashboard insights
→ render
```

Do not wait for an AI provider.

### Insights screen

``` text
read snapshots
→ render
→ detect stale fingerprints
→ refresh local calculations
→ update changed cards
```

### Stock movement

``` text
owner confirms
→ Inventory Service
→ exclusive transaction
→ no-negative-stock validation
→ commit
→ invalidate affected snapshot
→ recalculate local insight
```

### Optional online AI

``` text
local insight already visible
→ build minimum context
→ AI provider
→ structured response
→ Zod validation
→ optional AI snapshot
→ enhance explanation
```

If this branch fails, the local result stays visible.

## 15. Local-only security constraint

Do not ship a privileged reusable AI-provider API secret in:

``` text
.env
app.json
app.config.ts
JavaScript bundle
obfuscated source
```

SecureStore is appropriate for small sensitive values provisioned to the
device, but it does not make a provider secret safe if the application
itself must contain or recover that reusable secret.

For the current local-only architecture, use one of these:

1.  no external generative AI in v1;
2.  a provider with a safe client authentication design;
3.  later introduce a controlled backend/proxy.

For v1, option 1 is the cleanest.

## 16. Future on-device LLM

A true offline LLM can be added later behind the same provider
interface:

``` text
AIProvider
├── RemoteAIProvider
└── OnDeviceAIProvider
```

Do not make it the first implementation. On-device models add storage,
RAM, battery/thermal, native integration, model-distribution, and
device-compatibility costs.

The deterministic engine remains the primary fast path even after an
offline model exists.

## 21. What is StockPilot-specific

These are architecture decisions for StockPilot rather than requirements
imposed by Expo:

``` text
SQLite as inventory truth
local deterministic intelligence first
snapshot-first rendering
fingerprint invalidation
stale-while-revalidate insights
precompute after stock mutations
generative AI cannot mutate inventory
local response templates
AI is optional
strict store isolation
no negative stock
```

They follow directly from StockPilot's requirements: offline operation,
fast response, low cost, deterministic inventory rules, and safe stock
mutations.
